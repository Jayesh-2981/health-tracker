# Health Tracker — Data Model

## 1. Purpose

This document defines the data structures used by Health Tracker.

The initial health-tracking module is Blood Pressure.

The data model is designed so that additional health trackers can be introduced without changing the existing Blood Pressure data structure.

Google Sheets is the initial persistence layer for health records.

---

# 2. Data Model Principles

The data model should:

- Be simple and understandable
- Preserve data integrity
- Provide stable identifiers
- Support CRUD operations
- Be easy to represent in Google Sheets
- Be independent of the frontend UI
- Be independent of Google Sheets implementation details
- Support future health modules

The application should not store presentation-specific values as the primary data representation.

For example, the application should store:

```text
systolic = 120
diastolic = 80
```

rather than:

```text
bloodPressure = "120/80 mmHg"
```

The formatted representation should be generated by the frontend when required.

---

# 3. Blood Pressure Record

The initial Blood Pressure record contains:

| Field      | Type     | Required | Description                                                 |
| ---------- | -------- | -------- | ----------------------------------------------------------- |
| id         | string   | Yes      | Unique identifier for the record                            |
| recordedAt | datetime | Yes      | Date and time when the measurement was taken                |
| systolic   | integer  | Yes      | Systolic blood pressure value                               |
| diastolic  | integer  | Yes      | Diastolic blood pressure value                              |
| pulse      | integer  | No       | Pulse/heart rate measured with the reading                  |
| notes      | string   | No       | Optional user notes                                         |
| createdAt  | datetime | Yes      | Date and time when the application created the record       |
| updatedAt  | datetime | Yes      | Date and time when the application last modified the record |

---

# 4. Blood Pressure Object

The application-level representation is:

```json
{
  "id": "bp_01JXXXXXXXXXXXX",
  "recordedAt": "2026-09-10T08:30:00+05:30",
  "systolic": 120,
  "diastolic": 80,
  "pulse": 72,
  "notes": "Morning reading",
  "createdAt": "2026-09-10T08:31:15+05:30",
  "updatedAt": "2026-09-10T08:31:15+05:30"
}
```

The exact ID generation mechanism will be decided during backend implementation.

The ID must be unique and stable for the lifetime of the record.

---

# 5. Field Definitions

## 5.1 id

A unique identifier for the Blood Pressure record.

Example:

```text
bp_01JXXXXXXXXXXXX
```

The identifier must:

- Be unique
- Remain unchanged when the record is updated
- Be used for update operations
- Be used for delete operations

The ID should not depend on the spreadsheet row number.

This is important because spreadsheet rows can change when records are inserted, deleted, or reordered.

---

## 5.2 recordedAt

The actual date and time at which the user took the measurement.

Example:

```text
2026-09-10T08:30:00+05:30
```

This is different from `createdAt`.

A user may enter an older measurement later.

Example:

```text
Measurement taken:
2026-09-09 08:30

Entered into Health Tracker:
2026-09-10 10:15
```

Therefore:

```text
recordedAt ≠ createdAt
```

when a historical measurement is entered.

---

## 5.3 systolic

The systolic blood pressure measurement.

Example:

```text
120
```

The value is stored as a number rather than a formatted string.

---

## 5.4 diastolic

The diastolic blood pressure measurement.

Example:

```text
80
```

The value is stored as a number rather than a formatted string.

---

## 5.5 pulse

The pulse/heart rate associated with the measurement.

Example:

```text
72
```

This field is optional because a user may record blood pressure without recording pulse.

---

## 5.6 notes

Optional free-text information related to the reading.

Examples:

```text
Morning reading
```

```text
After exercise
```

```text
Before medication
```

The application should not require notes for every reading.

---

## 5.7 createdAt

Timestamp representing when the application created the record.

This should be generated by the backend.

The frontend should not be trusted to provide this value.

---

## 5.8 updatedAt

Timestamp representing when the application last modified the record.

This should be managed by the backend.

When a record is updated:

```text
updatedAt
```

must change.

When a record is not modified:

```text
updatedAt
```

must remain unchanged.

---

# 6. Google Sheets Representation

The Blood Pressure worksheet will use a structured table.

Initial columns:

```text
ID
Recorded At
Systolic
Diastolic
Pulse
Notes
Created At
Updated At
```

Example:

| ID     | Recorded At               | Systolic | Diastolic | Pulse | Notes           | Created At                | Updated At                |
| ------ | ------------------------- | -------: | --------: | ----: | --------------- | ------------------------- | ------------------------- |
| bp_001 | 2026-09-10T08:30:00+05:30 |      120 |        80 |    72 | Morning reading | 2026-09-10T08:31:15+05:30 | 2026-09-10T08:31:15+05:30 |
| bp_002 | 2026-09-09T21:15:00+05:30 |      128 |        82 |    75 | Evening reading | 2026-09-09T21:16:20+05:30 | 2026-09-09T21:16:20+05:30 |

The exact formatting of the spreadsheet may be improved later without changing the application data model.

---

# 7. Spreadsheet Row Mapping

A spreadsheet row maps to one application-level Blood Pressure record.

Example:

```text
Spreadsheet row
       │
       ├── Column A → id
       ├── Column B → recordedAt
       ├── Column C → systolic
       ├── Column D → diastolic
       ├── Column E → pulse
       ├── Column F → notes
       ├── Column G → createdAt
       └── Column H → updatedAt
```

The mapping should be centralized inside the Google Sheets integration layer.

The Blood Pressure domain should operate on application objects rather than spreadsheet rows.

---

# 8. Row Number vs Record ID

The application must not use the spreadsheet row number as the permanent record identifier.

For example:

```text
Row 2 → bp_001
Row 3 → bp_002
Row 4 → bp_003
```

If `bp_002` is deleted:

```text
Row 2 → bp_001
Row 3 → bp_003
```

The record identity remains:

```text
bp_003
```

even though its physical spreadsheet row changed.

This prevents CRUD operations from becoming dependent on spreadsheet layout.

---

# 9. Date and Time

The application should use a consistent date/time representation internally.

API timestamps should use ISO 8601 format.

Example:

```text
2026-09-10T08:30:00+05:30
```

The UI may display a localized format such as:

```text
10 Sep 2026, 8:30 AM
```

but the underlying value should remain machine-readable.

The application should distinguish between:

- Measurement time
- Record creation time
- Record modification time

---

# 10. Validation

The backend must validate all Blood Pressure records before persistence.

Validation will include:

### id

Generated by the backend.

The client should not control the identifier during record creation.

### recordedAt

Must be a valid date/time.

### systolic

Must be an integer.

### diastolic

Must be an integer.

### pulse

If provided, must be an integer.

### notes

If provided, must be a string.

The exact acceptable numeric ranges and additional domain rules will be finalized during implementation.

Validation rules should avoid pretending to provide medical diagnosis.

The application records measurements; it does not independently diagnose medical conditions.

---

# 11. Create Operation

When creating a Blood Pressure record, the client provides:

```json
{
  "recordedAt": "2026-09-10T08:30:00+05:30",
  "systolic": 120,
  "diastolic": 80,
  "pulse": 72,
  "notes": "Morning reading"
}
```

The backend generates:

```text
id
createdAt
updatedAt
```

The complete record is then persisted.

---

# 12. Update Operation

When updating an existing record, the record ID identifies the target.

Example:

```text
PUT /api/v1/blood-pressure/bp_001
```

The backend must:

1. Verify that the record exists
2. Validate the updated data
3. Preserve the record ID
4. Preserve the original `createdAt`
5. Update `updatedAt`
6. Persist the changes

---

# 13. Delete Operation

Delete operations use the stable record ID.

Example:

```text
DELETE /api/v1/blood-pressure/bp_001
```

The backend must identify the corresponding spreadsheet record using its ID rather than assuming a fixed row number.

---

# 14. Read Operations

The application should support retrieving:

### All records

```text
GET /api/v1/blood-pressure
```

### Individual record

```text
GET /api/v1/blood-pressure/:id
```

The API should return application-level objects rather than raw Google Sheets rows.

---

# 15. Sorting

The backend should return Blood Pressure records in a predictable order.

The default ordering should be based on:

```text
recordedAt DESC
```

so the newest measurement appears first.

The frontend should not need to understand spreadsheet ordering.

---

# 16. Future Health Modules

Additional health trackers will have their own data models.

For example:

```text
Blood Pressure
├── systolic
├── diastolic
├── pulse
└── ...

Weight
├── weight
├── unit
└── ...

Blood Sugar
├── glucose
├── unit
├── measurementContext
└── ...

Heart Rate
├── heartRate
└── ...
```

Each module should define its own domain-specific fields.

Shared concepts such as:

```text
id
recordedAt
createdAt
updatedAt
notes
```

may be reused where appropriate.

They should not be forced into every health module if they do not make sense.

---

# 17. Data Storage Abstraction

Although Google Sheets is the initial persistence layer, the domain model must not depend on Google Sheets.

Conceptually:

```text
Blood Pressure Domain
        │
        ▼
Persistence Interface
        │
        ▼
Google Sheets Implementation
```

This allows a future storage implementation such as PostgreSQL to be introduced without rewriting the Blood Pressure domain logic.

The application should not assume that Google Sheets is the only possible persistence mechanism.

---

# 18. Data Ownership

Health records belong to the authenticated user.

The backend must ensure that a user can only access and modify the Google Sheets resources that the application has associated with that authenticated user.

A user must never be able to access another user's health records by changing a record ID or request parameter.

Authorization must therefore be enforced server-side.

---

# 19. Data Privacy

Health data is sensitive personal information.

The application should minimize the amount of health information stored outside the user's Google account.

The backend should avoid logging complete health records unnecessarily.

Logs should not expose sensitive user data unless required for controlled debugging.

---

# 20. Future Data Model Changes

Changes to the data model should be deliberate.

When a field is added, removed, renamed, or changes meaning:

1. Update this document
2. Update validation
3. Update API documentation
4. Update Google Sheets mapping
5. Update frontend forms
6. Update tests
7. Consider compatibility with existing records

Existing user data must be considered before changing spreadsheet column structures.

---

# 21. Current Scope

The initial data model contains only the Blood Pressure record.

The following are intentionally deferred:

- Blood Sugar model
- Weight model
- Heart Rate model
- Medication model
- Sleep model
- Complex medical terminology
- Medical diagnosis logic
- Automated medical recommendations

These will be designed when their respective modules are implemented.
